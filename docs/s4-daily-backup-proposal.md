# S4 每日备份评估（仅方案，未启用）

- 目标：将当前“上次部署”的 RPO 收窄到约 24 小时；同盘快照仍无法覆盖宿主机损坏。
- 建议：用户确认后增加 systemd oneshot service + timer，每日 UTC 19:00（韩国 04:00）。
- timer 拟用 `OnCalendar=*-*-* 19:00:00 UTC`、`Persistent=true`、`RandomizedDelaySec=10m`。
- 每日定时与补跑均需失败告警；计时器触发成功不代表备份校验成功。
- service 使用独立“只备份”入口，共用 S4 隔离容器双库代码，绝不调用更新/拉取/重启流程。
- 提取共用入口及定时运行回归测试留待下一任务；当前 `linux-update.sh` 不能当定时备份入口。
- 复用 backend 镜像 ID、128 MiB 限额、SQLite Backup API、integrity_check 与宿主机 SHA-256。
- 沿用当前部署快照命名及保留规则，以当前完整提交的前 12 位和 UTC 时间戳生成文件名。
- 不更改 `backup_retention.py`；每次双库校验成功后才分别运行现有保留器。
- 使用 `flock` 与部署入口共享同一把锁，避免并发备份/清理；锁改造也需单独实现测试。
- 备份前后复用默认 15 GiB 门槛和未管理文件清单；超限时失败告警，保留所有已有快照。
- 建议进一步检查剩余空间 ≥ 双库大小 + 2 GiB，避免仅依赖目录上限。
- 用 journald 记录开始/完成时间、版本、文件名、大小、校验和及退出码；不记录环境机密。
- service 的账户、Docker 权限与 `backups/` 访问权最小化，配置不写进仓库 `.env`。
- 先在测试机连续三天验证双库与并发锁，观察业务容器内存、耗时和磁盘增长。
- 每周抽样执行恢复演练；另外评估加密异机副本、访问控制与保留成本。
- 启用前由用户决定：时区/时段、24 小时 RPO 是否足够、告警渠道、异机目的地及容量预算。
- 上线应另行提供 service/timer 文件和启停步骤；本任务不创建 unit、不运行 systemctl 或 cron。
