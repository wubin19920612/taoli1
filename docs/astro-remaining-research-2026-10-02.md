## 1. FR 仓位价值倍率：方向、规划、零头和限制

### 参数含义及限制

**B，E31–E35：** 找到独立价值比例模块 `anonymous_93 @0xf00000121300`，导出 `getPositionValueRatio/getPositionValueScales/planOpenValues/getPositionValueError/selectRatioOpenQuantities/ensureProportionalCloseMinRate`。FR 主模块明确导入这些函数，不能再把 `positionValueRatio` 视为纯显示字段。

设 `r=positionValueRatio`，两腿仓位价值为 A、B。误差函数 `dS(r,A,B)` 的原始算术是：

```text
error = A - r * B
目标：A / B = r
```

例如 r=2 的目标是 A 价值200、B价值100，而不是 B 是 A 的两倍，也不是币数比2。

- 仅 FR 使用自定义价值倍率；其他策略的 getter 返回1。
- 合法范围包含端点 `[0.1,10]`，0.1 已从原始 float64 解码，10为立即数。
- 配置校验拒绝范围外参数；运行时 getter 对异常参数回退1。这是两个入口的不同处理，不应在自建配置层静默采用回退。
- 空参数及1存为无自定义倍率；非1时，禁止非空 `stepOpen/stepClose`，禁止 `usdcNoTrade === true`。
- 配置要求 `maxNotional` 和 `maxTradeUSDT` 至少容纳 `minNotional * max(r,1/r)`。默认最小12、单笔最大100。较大倍率会使较小腿无法满足最小金额，校验是为此设置；`max` 名称由上下文及明确错误文案推断。
- `regressionValue` 只在 FR/SR 接受正数；不是线性回归模型的计算结果生成器，这一入口仅接收参数。

### 开仓价值规划

**B+语义推断，E33/E34：** `lN` 和 `LJ` 的算术及调用关系可还原为以下公式。min/max 的 RO 名称尚未由匹配 snapshot 直接解析，公式的 min/max 解释由 larger-leg 语义、上限约束及相同 RO 在多处的使用交叉支持。

```text
sA = min(r, 1)
sB = min(1/r, 1)
L  = max(A/sA, B/sB)
Lnext = min(maxLargeValue, L + largeIncrement)
addA  = max(0, Lnext*sA - A)
addB  = max(0, Lnext*sB - B)
```

其中返回的 `aValue/bValue` 是本次增量，不能把它当目标总仓位。`maxLargeValue` 限制较大腿，不能直接当组合两腿总名义金额上限。例如 r=2、A=120、B=100、增量20、上限300，输出 addA=100、addB=10、Lnext=220；最终220:110。已有失衡时，较弱一腿的补入可能大于 largeIncrement，后续每腿单笔额度必须继续检查。

**B，E36–E39：** 数量候选函数的细节也已找到：

1. 两边候选数量都大于0，直接返回两边数量；该函数本身不是全局风险校验器。
2. 只有一边可下单时，构造 A 单腿、B 单腿候选；缺少候选的那边还尝试最小下单量。
3. 只允许恰好一边新增价值为正、且新增后 `abs(A-rB)` 严格缩小的候选；比较里有一个 Number 根常量，按 EPSILON 语义解释。
4. 按新增后的绝对误差升序选择；没有改善候选返回 `(0,0)`。

这说明“比例策略允许单腿动作”和“普通套利意外单腿”是不同业务状态。自建需把 `RATIO_REBALANCE` 与 `FAILED_HEDGE_RECOVERY` 明确区分，并在任何单腿动作之前计入未决订单。原函数可能提出最小量候选，自建不能因此绕过资金/深度/单笔预算。

### 平仓最小比例及尾仓

**B+语义推断，E40/E41：**

```text
shouldCloseAll = closeRate >= 1
                 OR (aLeft < 2*aMinQty AND bLeft < 2*bMinQty)
floorRate = max(aMinQty/aPosition, bMinQty/bPosition)
若两腿仓位均>0、floorRate为有效有限数且<=1：
    closeRate = max(closeRate, floorRate)
否则保留原closeRate
```

严格 `<` 的边界不能写成 `<=`；两腿残量条件是 AND。这是局部尾仓规划，仍应受 reduce-only、实际持仓、合约步长及单笔上限限制。自建超出单笔限额时拆片，不能把“全平”解释成无上限市价单。

## 2. FR/SR 价格倍率、回归参考值与触发阈值

**B，E42–E45：** 找到两套相关转换，不应混淆：

- 成交均价显示 `PN`：FR/SR 无有效回归参考值时返回原始 `A/B` 的格式化值；该分支没有应用 rateMultiply。
- 有参考值 R 时，先 `x=(A/B)*m`，再显示 `200*(R-x)/(R+x)`，这里数值单位是百分数。
- 价格告警转换 `Bp`：先将原始比率乘 m；无有效 R 时返回乘过倍率的值，有 R 时再用同一对称偏离百分数公式。
- 因而“无回归参考值时的均价显示”和“价格告警”对倍率的处理并不完全相同，迁移卡片时不能拿 UI 文本当执行阈值。

倍率表的数值路径包括 `10^3/10^6/10^9/10^12`、`10^-3/10^-6/10^-9/10^-12`、默认1。倒数标签 `1/K,1/M,1/B,1/T` 为直接字符串，值已解码；正向单字母标签存在 RO 映射失真，不能把伪代码中出现的 `eval` 当作真实用户选项。

此前已确认 FR 主循环开仓 `Aask/Bbid < openThreshold`、平仓 `Abid/Bask > closeThreshold`。本轮不能把显示函数直接替换主循环阈值：完整 UI/SDK 输入到缓存阈值的映射仍需独立回放确认。

**S：** 新系统内部只保存一种带类型的执行阈值 `raw_ratio`，UI 明确显示单位、倍率和参考值。若支持百分偏离 d 到原始比率转换，独立实现：

```text
x = R * (200-d)/(200+d)
raw_ratio = x/m
```

要求 R>0、m>0、-200<d<200，使用十进制定点数。输入百分偏离增加，原始比率降低；比较方向必须随转换反转。与普通 SF/FF 的小数价差阈值完全分开。未经回放核对的旧 Astro 卡片仅导入为禁用状态。

## 3. 单腿恢复：已还原的 SF 决策及适配器差异

**B，E46/E47：** SF 主循环中的恢复规则如下，适用该样本和该函数，不能泛化所有六类策略：

| 条件 | 行为 |
| --- | --- |
| TradeData 对应卡片 Map 为空 | 退出该恢复处理段，随后继续常规判断 |
| 已 stopTrade、处于强制减仓、recoverSingelLegTimes 尚未置位 | 将该标志置1，singleLeg=0，stopTrade=false，换为空 Map，然后结束本次恢复处理 |
| 尚未超等待时间 | 不执行本段重试 |
| 超等待时间且 Map.size>=2 | singleLeg=1、stopTrade=true、异步重算均价，记录“两条腿都失败” |
| Map.size==1 且 times 达上限 | singleLeg=1、stopTrade=true、重算均价，记录抢救失败 |
| Map.size==1 且未达上限 | 更新交易时间戳，调用记录内 reOrderCallback |

等待时间：A 侧为 `okxdex/uniswapv3/pancakeswapv3/jup` 时38000ms，其他为8000ms。比较为 elapsed > limit。上限普通2、强制减仓12；记录有 `retry100times` 真值时覆盖为100。此数字是记录 `times` 的判断阈值，不能不看初始计数就声称恰好新增下单2/12/100次。

`recoverSingelLegTimes` 是一次恢复分支标志，不是通用重试预算。恢复段结束后常规逻辑又把卡片 `reOrderTimes` 清零，适配器闭包则复制参数并递增 reOrderTimes。两者所处层次不同。

**B，E48–E50/E59：**

- HL 的 `anonymous_961`、Lighter 的 `anonymous_1058` 回调包含复制请求参数、重试次数加1并再调适配器；闭包自身没有证明重发前做了终态核对，外围仍可能有保护。
- `daysInYear_2 @0xf00000558a00` 则明确读取 TradeData 的 `retryAllowed`，为假时返回并记录 prior order must be terminal。名字是反编译器生成，不能据它判断业务含义。
- 共享 `hasPendingTradeConfirmation` 遍历记录，发现有效 `confirmationPendingUntil > now` 就返回真。到期返回假只是此门槛失效，不等于订单明确未成交。
- 本轮穷举出33个带 reOrderTimes 的短闭包，证据文件保留地址及局部门槛字面量。这个清单完成了入口盘点，不代表33个端到端平台协议全部验证。

**S：** 可模仿的是按卡片冻结、异步核对、受控恢复的机制；不复制“Map条数=真实订单状态”的假设。使用账本中的 FILLED/PARTIAL/REJECTED/UNKNOWN 判断，先确定历史订单可能成交的余量，再选择补另一腿或退出原腿。超时、限流、5xx、断连均不自动允许换ID下单。重试次数、累计金额、最坏敞口、价格保护和恢复截止时间共同约束；截止只隔离/告警，不能抹掉 UNKNOWN。

## 4. 持久化和重启：现在能确认到哪一步

**B，E51–E54：** 完整追踪到 `addPendingOrder=E4` → `GN` → `anonymous_159`。

1. E4 以 `(pairId,type,coin)` 组合成逻辑键，更新主 Map 和 reqId 反向 Map。同逻辑键新 reqId 会替换旧记录及其反向映射。它不是保存任意多个在途订单的追加日志。
2. GN 做 `writeChain=writeChain.then(flush)`，随后返回 undefined，不把刷盘 Promise 返回调用者。
3. flush 序列化当前集合，await writeFile 临时文件，await rename 到正式文件；错误捕获后记录日志，该函数没有可见 fsync 调用。
4. 删除请求也更新内存后调用 GN；此前 Uye 恢复查单后、状态处理前调用删除函数的顺序仍成立。

可确认的结论是：此 pending 接口本身不提供“返回即已耐久保存”契约；原子重命名不等于断电持久化，也不与 SQL 仓位更新组成事务。不能据此断言用户服务器已丢单，因为还需要当时调用路径、文件系统和运行时事实。

**S：** 单写者 SQLite WAL 事务先保存 intent、预算预留、稳定 client ID 与发送权限；提交达到约定持久级别后才放行网络发送。fill唯一键、订单投影、仓位、预算和待核对状态同事务更新。备份恢复后先对账再开策略，保留所有 UNKNOWN。不要用 `(pairId,type,coin)` 覆盖不同订单。

## 5. 行情新鲜度：完整分段阈值及 boost 的真实含义

**B+语义推断，E55/E56：** 基础最大盘口年龄950ms、两盘口时间差300ms。每卡片两本 FrequencyMonitor 容量100。以下 max 和绝对值函数名称由共同 RO 用法推断；倍数和分支边界均来自指令及原始 float64。

设 t=max(两个平均更新间隔)，输出 `(maxAge,maxSkew)`，单位ms：

| 统计状态 | 普通场所 | hasHl 或 hasOkxdex |
| --- | --- | --- |
| 任一间隔<=0 | (950,300) | (7600,2400) |
| 两者>0且t<=400 | (max(950,3.8t), max(300,2.2t)) | (2850,900) |
| 400<t<=800 | (1425,450) | (2850,900) |
| 800<t<=2000 | (7600,2400) | (7600,2400) |
| t>2000 | (19000,6000) | (19000,6000) |

之后 boost 为真时两值×1.5；否则 slow 为真时×0.6；两者同真由 boost 分支优先。`now=Date.now()+AVG_TIME_DIFF`；任一本时间戳大于 now+2000 拒绝。盘口年龄或两本时间差严格超过对应阈值拒绝。

不能把“950ms”写成所有场景的绝对失效线：稀疏更新分支可以容忍19秒，boost后28.5秒。自建对套利采用独立硬上限，动态统计只能在硬上限内调节；分别记录源时间、本机接收单调时间、序列完整性和时钟质量，不因交易品种冷清而无限放宽交易数据有效期。

## 6. 下单成功与成交成功：HL/Lighter 的实际边界

**B，E57/E58：**

- HL `Aw` 检查提交响应的 status、response.type、statuses 数组及错误项，无错误时打印 success 并返回；这条成功返回路径未把实际成交量直接写入仓位。不能将 success 日志解释为两腿已成交。
- HL 客户端 IOC 默认 slippage 解码为0.01，但上层 Aw 明确传入0.1。因此讨论策略此路径应使用10%的名义限价偏移，不能拿客户端默认1%覆盖上层参数，更不能读成0.1%。最终成交滑点仍取决于盘口和执行结果。
- Lighter 工厂分别导出 spotTrade/futureTrade，future 路径可见签名/序列化后 POST、检查 HTTP200 和响应 code200，然后 success 返回。请求带 `price_protection=false`；只能据此描述该 API 参数，不能声称完全没有其他价格限制。
- Lighter 账户处理代码另有 `account_all_trades`、订单 `filled`、filled_quote_amount/filled_base_amount 和仓位更新路径；另一个费用映射函数使用 ask/bid account ID 匹配方向、maker/taker身份和字符串 client/trade ID。提交ACK、订单状态、成交费用确实分不同路径处理，完整去重与断线回补仍需协议级测试。

**S：** 适配器统一暴露提交事实和成交事实，而不统一假造“成功”：

| 结果 | 内部状态 | 允许动作 |
| --- | --- | --- |
| 请求已受理，没有 fill | ACKED | 接收私有流、按ID核对；不更新成交仓位 |
| 部分成交 | PARTIAL | 累积真实成交增量；剩余量继续计入最坏敞口 |
| 明确拒绝且确认无成交 | REJECTED | 释放该订单余量，按切片风险做恢复 |
| 超时/断连/结果不可解释 | UNKNOWN | 保留预算、查单与补成交；禁止盲重发 |
| 撤单回执 | CANCEL_PENDING 或已核验 CANCELED | 仍接收晚到成交，不以HTTP撤单成功替代成交核对 |

CEX、HL、Lighter、链上 AMM 的确认机制不等价。CrossEx 上轮8/8/8/5门槛保留为专用通道结论，不上升为平台通则。

## 7. 网格：发布版证据与历史文档冲突

**B：** 主文件迁移内容显示：版本3加入 coinPair.gridCount、buyIndex、order.gridIndex；版本4删除 buyIndex；版本8删除 gridCount 和 gridIndex。本轮在完整主文件线性输出中查找 grid/Grid，命中迁移定义；发布包15个前端 JS 对 `gridCount/gridIndex/网格` 均零命中，文件哈希已记录。

**D：** 历史 grid-reference 文档规定等距汇率格、每格预算、启动只买当前位置上方一格、跨下边界买、跨上边界卖、部分成交不切换满/空状态、整格退出才结算收益。

**结论：** 当前样本不足以证明仍有独立旧网格执行器。不能把旧文档升级成已恢复的1.9.24源码，也不能仅凭零字符串命中证明不存在其他实现。后续自建网格采用独立产品规格；若用户当前版本确有该功能，需要对应版本或具体操作入口做对照。

**S，可实现边界规则：** 格子i的上边界 `U-(i-1)Δ`、下边界 `U-iΔ`，Δ=(U-L)/N。开仓使用实际买A卖B比率，严格低于下边界才买；平仓使用实际卖A买B比率，严格高于上边界才卖。恰好边界不动，避免双归属。越界价格仍逐格按已确认状态及总预算处理；不凭一次跨越同时发满所有格子。每格保存 confirmed数量、pending余量、成本和费用；BUYING/SELLING中不能重复建单。N>=2、U>L>0，每格金额足够两腿规格，旧文档示例利润率只是毛估算，必须扣四次成交费用、滑点和资金费。

| 所有CEX/DEX的完整重试/去重协议 | 33个重试闭包盘点、关键通道追踪、统一未知状态契约 | 每个启用适配器的官方协议、录制回放及故障测试 |
| FR/SR旧卡片UI阈值端到端映射 | 比率方向、显示/告警公式、价值规划已定位 | 固定输入卡片经过原UI/SDK导出值的安全隔离对照 |
| 实际吞吐与双腿成交时间差 | 热路径、隐藏await、缓存/nonce/签名链、计时点已明确 | 同服务器/同网络/同负载实测；静态逆向不能证明性能相同 |

这些边界不阻止独立开发 SF/FF 与风险账本，也不需要继续等待全文件高级反编译。但若目标是所有旧卡片无差异迁移、所有平台行为兼容，则这些项目仍是必要验收，不可以改名为已完成。

## 9. 自建系统的最终实施路径

保留雷达 Python/FastAPI/React；增加 TypeScript/Node LTS strategy-worker 和独立 trade-gateway。worker不持密钥，网关校验市场身份、有效盘口、共同经济敞口、单笔及账户预算、费用/资金费周期、交易意图持久性和实例发送权限。热路径使用内存盘口和规格缓存，签名/nonce按账户实际隔离域排队，数据库单写者，不在一次性发送窗口内临时抓取另一边的mid或规格。

1. **账本/mock阶段**：实现订单/切片/策略三层状态、预算预留、唯一fill、UNKNOWN核对、恢复隔离。先跑超时已成交、部分成交、撤单晚成交、重复乱序、崩溃恢复、双策略争用预算。
2. **一DEX一CEX阶段**：确认Arcus身份后决定是否作为首个DEX；只支持核验过的线性同标的、1–3个市场，接完整发现/行情/账户/下单/查单/成交/费用，而非只接下单URL。
3. **执行时序阶段**：顺序切片IOC先验收，再开放受保护并行。并行前两腿都完成预算预留、规格/价格确认、可发送准备；统一短窗口连续放行。任一腿可能单独成交，必须有可承受的风险预算。
4. **扩展策略阶段**：FR价值比例、价格回归显示、阶梯、网格分别验收；参数类型与风险规则分开。比率策略不是保证无风险的同标的套利，不以统计参考值替代经济敞口校验。

性能报告必须分别给出事件接收→决策、准备、传输提交差、ACK差、首笔/最终成交差、未对冲名义金额×持续时间；既记录p50/p95/p99，也保留最长尾部和失败率。本机发送差p99≤5ms仍是目标，不是本轮测量结果。Node事件循环连续调用不保证跨交易所同步成交，换成Rust也不能消除网络和撮合差异。
