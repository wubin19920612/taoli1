# Astro 相似系统的实施阻塞项复核

日期：2026-10-02。研究模块，不实现或部署交易服务。基线 `486cca9`，分支 `codex/frontend-localization-polish`。目标：判断尚未恢复的 Astro 细节是否妨碍构建完整相似系统，并继续调查真正影响参数兼容和资金安全的部分。

## 结论与“完整”的验收范围

可以独立构建具有卡片配置、行情计算、SF/FF/FS/SS与FR/SR策略、阶梯、双腿执行、账户与风险控制、成交账本、收益统计、重启恢复和可扩展适配器的系统。无需恢复全部原始源码，也无需照搬 Astro 的持久化或重试实现。当前研究不是这些模块已经开发完成的证明。

不能承诺未经逐平台测试就覆盖 Astro 的全部交易所、所有账户模式、链上协议、自动借币/调资功能及历史卡片细节；也不能承诺相同收益、实盘吞吐或成交时间差。下表把影响落实到具体交付，而不是笼统称作“还有未知”。

| 未决项 | 对独立实现的影响 | 本轮处理/结论 |
| --- | --- | --- |
| 原始JS还是TS、完整变量名、V8 RO名称 | 不阻塞业务独立实现 | 沿用TS/Node执行服务；关键公式采用明确类型与测试，不运行伪源码 |
| FR/SR UI到内部阈值 | 会影响兼容导入和人工配置 | 本轮找到前端明文转换、提交封装、核心赋值，核实纯数学函数；完整UI事件/HTTP/核心动态对照仍未运行 |
| 成交去重、部分成交、断线回补 | 阻塞安全实盘 | 已进一步追踪HL/Lighter回调；必须独立实现事务账本和事实去重，逐适配器验收 |

## 1. 本轮补齐FR/SR参数链

发布包 `astro-admin/dist/assets/index-Cbqo_kH4.js` 含可读函数。其与 `main.jsc` 来自同一已校验1.9.24发布包。完整哈希、UTF-8偏移、提取函数见 [证据文件](research/astro-implementation-blockers-evidence-2026-10-02.json)。

### 表单展示与提交

设内部阈值q、显示倍率m、有效回归参考值R：

```text
无R：表单展示 = q*m；提交阈值 = 表单值/m
有R：表单展示 d = 200*(R-q*m)/(R+q*m)
     提交阈值 q = R*(200-d)/(200+d)/m
```

这次已从原前端 `ao/Lo/zn/In/Mo` 确认，不再只是独立代数推导。倍率直接映射 T/B/M/K/1/1K倒数系列到10的相应幂，解决此前正向单字母RO标签失真的问题。

- 前端 `qi` 将百分数夹在 `[-199.999999,199.999999]`，不是对所有越界值直接拒绝。界限由 `kn=6; em=200-10**-kn` 定义。
- 展示进入表单时有舍入：百分偏离6位；无R普通比率6位；部分金额/止损/告警转换使用12位。打开表单再保存可能带来量化差异，不能把它当精确无损往返。
- 普通SF/FF/FS/SS表单百分数提交前除100并保留4位小数；例如1.68提交为0.0168。FR/SR提交的是原始比率，不再额外除100。
- `regressionValue` 有效时保持与乘过m的比率同一显示尺度。改变m时，前端同步按新旧倍率比缩放R；有回归参考值时不应又重复缩放百分偏离。
- 提交函数要求FR/SR开仓原始比率小于平仓原始比率；其他策略反向。核心 `Npe` 将输入openPosition/closePosition转数值并赋给缓存，没有在该赋值段再次乘m。
- HTTP封装 `OF` 将对象展开后 POST `/api/config/update-pair`，此封装本身不再变换数值。没有调用这个写接口。

### 模式切换与阶梯

前端保存逻辑依赖之前的回归模式引用 `y.current` 和当前输入R。回归输入失焦回调 `Ca` 会变换开/平/止损/阶梯字段；从无R变有R或反向时，还会转换并交换greaterPriceAlert/lessPriceAlert。原因是百分偏离与原比率单调方向相反。不能只复制数值不复制方向。

阶梯提交同样先把百分偏离变回比率，再除m；其保存精度为12位。普通策略阶梯百分数除100后4位。FR/SR阶梯开仓阈值逐级降低、目标仓位逐级升高；平仓阈值逐级升高、目标仓位逐级降低。前端FR非默认价值倍率禁止阶梯，这与核心配置校验一致。

FR反向复制还会交换交易腿与原始市场/DEX信息、取倒数倍率、取倒数价值比例、以旧close倒数作为新open、以旧open倒数作为新close，并处理告警方向和回归参考值，删除旧止损/阶梯。只交换交易所名称会生成错误策略。

**影响与决策：** 已有足够依据实现正常表单/导入的数值规范；全旧UI事件兼容仍不能宣称验证完成。自建采用一个无隐藏UI引用的规范化转换入口，导入时保存原字段、显示单位、规范值、舍入差、原始市场身份，并默认禁用。极端百分输入超过合法范围直接拒绝并说明，不复制静默夹值行为。调用者已提交规范值时不得重复转换。

### 实际执行的验证

仅提取并检查9个纯函数 `zn/eT/In/qi/nn/ao/Lo/tm/mT`，执行其原文，依赖限于Number/Math和两个显式数值常量。29项检查通过，覆盖九种倍率及倒数、参考值归零、百分逆变换、极值夹值、告警方向交换、无效参考值、倍率变更不变性。

这比上一轮独立参考公式增加了原发布函数的局部执行证据，但不是完整UI、API、核心或实盘等价测试。未执行完整bundle、`.jsc`、WASM或安装入口。

## 2. 成交入账的进一步追踪

新增原字节核验E60–E63，共586条指令；区域与原文件偏移见证据。以下只描述被追踪路径，不声称整个产品一定存在相关故障。

### Hyperliquid userFills

`anonymous_678 @0xf00000414600`：

1. `data.isSnapshot`为真直接返回此userFills处理分支。
2. 为当前消息建立Map，按cloid聚合fills，数量和费用求和，价格按成交数量加权。
3. 查询关联订单/TradeData；找不到记录有订单迟到日志路径。
4. 移除内存orders和对应TradeData记录；读取原记录size、times、rate。
5. 比较 `fillSize/rate` 与记录size，不相符时输出警告；该局部路径仍继续后续费用和入账调用。
6. 调用 `updateOrder` 与 `updateCoinPairPosition`，看到价格×rate、数量÷rate的对应换算；这里没有走此前识别的 `casFillOrder` 名称。

因此，同消息内按订单聚合不等于跨消息按fillID持久防重；忽略snapshot也不等于已具备断线回补。不能根据其他函数存在CAS就推出这条路径具备同样事务语义。完整外部防重、补查或平台消息保证仍需协议与动态测试。

### Lighter filled路径

`anonymous_1475 @0xf00000804700`：

- 该订单分支筛选status等于filled；检查client_order_id。
- 从filled_quote_amount/filled_base_amount计算成交均价，再查询订单跟踪记录。
- 读取原跟踪记录的size，移除内存跟踪；取费用缓存并记录完成时间。
- `updateOrder` 和 `updateCoinPairPosition` 的数量参数来自这个原记录size，而不是在这两次调用处直接采用filled_base_amount。

这说明此路径依赖“filled与原记录数量一致”等外部前提。不能把这段当成适用于部分成交撤余、不同字段口径的平台通用实现；也不能仅凭局部观察宣布线上仓位必然错误。

### 自建必须满足的规则

这些未完全恢复的私有路径不阻止设计，但实盘前必须验证替代实现：

| 输入事实 | 必须成立的处理 |
| --- | --- |
| 独立成交ID重复/乱序 | `(账户,场所,成交ID作用域,成交ID)`唯一；成交量只入账一次 |
| 平台仅提供累计成交 | 保留原累计值与版本/游标，差分不为负；重置或语义不明时隔离查单 |
| 累计数量与独立fills同时到达 | 指定一个仓位记账来源，另一路做核对；不两次加仓 |
| ACK显示成功，无fill | 只更新受理状态，不增加成交仓位 |
| 部分成交撤余 | 已成交部分入账，确认撤余后才释放余量预算 |
| 已移除本机跟踪后晚到fill | 从持久订单索引恢复关联，不能静默忽略 |
| 手续费晚到或以基础币收取 | 独立费用调整事件；基础币净持有量与名义成交量分开 |
| 断线重连/进程重启 | 在保持冻结的状态下合并快照、历史fills、订单和持仓；重放幂等 |

fill事件、订单投影、策略仓位、预算变动同事务提交。订单“终态”不等于成交信息永不补充；保留可追溯索引和晚到事件处理。支持的每个场所必须明确ID唯一域、分页/游标、历史保留期限和账户净额规则。

## 4. 可执行的模块验收顺序

“完整系统”应以业务闭环验收，不以“已复制多少个Astro函数”验收。

1. **基础核心**：原始市场/DEX身份、规格版本、定点价格数量、快照/增量盘口重建、策略参数规范化、卡片持久化、暂停/禁开/仅减仓。
2. **资金安全闭环**：账户共享预算、持久订单意图、发送实例隔离、实际fill记账、UNKNOWN核对、部分成交补腿、重启对账、费用/资金费周期及收益审计。
3. **策略完整性**：六类策略分别明确现货库存/借币前提及多空含义，阈值/阶梯/比例再平衡分别回放。SS/FS/SR若需要卖出无库存现货，必须有已核验借币能力与额度，不模拟成普通现货卖单。
4. **场所完整性**：每个启用适配器实现市场发现、行情、账户、准备/发送/撤单/查单、成交流、费用、限流、nonce与签名。AMM另验gas、nonce、链重组和最终确认，不套订单簿成交模型。
5. **产品与运维完整性**：卡片、浮窗、告警、审计、备份恢复和密钥隔离；自动借币/调资若纳入范围，单独增加资金流状态机、幂等核对、费用和额度约束，不作为双腿撮合的隐式副作用。
6. **性能完整性**：事件接收至决策、准备、传输提交差、ACK差、成交差及风险持续时间分开统计；含缓存缺失、签名排队、写盘延迟、限流及断连。先在mock和shadow测量，才有证据评价与Astro相似程度。

Arcus的官方入口仍是平台接入的真实信息缺口。本次没有重复请求该信息，也没有替换为猜测的同名平台。无需等待它就能完成基础核心和mock验证，但不能宣称已完成Arcus适配器。
