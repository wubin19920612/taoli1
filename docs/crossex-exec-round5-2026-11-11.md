## 简化原则
- **停开锁拆成彼此独立的集合。** 每种锁只能由它自己的条件解除，不能互相覆盖，也不能顺带清掉别的锁。`unhedged` 和 `repair_stopped` 只能在两腿远端实仓相等（含都为 0）、且补平已结束时解除；HALTED 只能人工解除。
- **本地流水和远端实仓分开存。** 本地流水 = 成交累计；远端实仓 = 持仓接口返回的数量。远端数据不得覆盖本地流水。对账时比较两者：成交记账还没完成时，只等待，不解锁。
- **只要有非终态订单（SENT 或 UNKNOWN）就要恢复。** 每一轮跟踪都检查，不依赖数据库写入是否成功，也不依赖账户检查是否成功：先查单，再撤单，再查两腿实仓，按实仓平仓或补平。启动时同样执行一遍。从未发出的 INTENT 在启动时直接转为 UNSENT。

## 要修的
1. **P1｜engine.py:263**：`position_mismatch` 覆盖了补平失败的原因，连续三次匹配后清掉了停开锁，裸露还在却恢复了开仓。改用独立锁集合修正。
2. **P1｜engine.py:488、252**：远端持仓覆盖了本地基准，掩盖了真实的流水差异。改为流水和实仓分开存，记账未完成时不解锁。
3. **P1｜engine.py:376、execution.py:150**：一条腿发送超时后，写 UNKNOWN 状态失败了一次，结果跳过了持仓重建，另一条腿已经成交的裸仓没人管。改为：写库失败时，内存里照样标记“需要恢复”，并重试写库；跟踪循环只看订单的非终态，不看写库结果。
4. **P1｜engine.py:235**：午夜之后、新一天第一次快照之前，如果隔夜亏损仓位被平掉，新一天的基准会算错。改为每次跟踪都保存各持仓的浮亏，跨日时以**午夜前最后一次保存的值**作为当日基准，即使仓位已经平掉也用这个值。
5. **P2｜engine.py:180**：HALTING 状态重启时，如果第一次账户检查失败，会跳过订单恢复，INTENT 永远转不成 UNSENT，进程一直卡在 HALTING。改为订单恢复不依赖账户检查。

## 故障注入不变量测试（必须新增）
用假交易所和假数据库写一个随机模拟器：固定随机种子，跑 ≥2000 个回合。每一步随机注入以下故障：
- 部分成交或零成交；
- 下单超时，事后补回 ACK 或 UNKNOWN；
- 查单失败、持仓接口失败；
- 数据库写失败一次；
- 进程重启（从数据库恢复）；
- 跨越 UTC 午夜；
- 盘口过期或价差消失；
- 价格大幅反向（触发止损和熔断）。

每一步之后都要断言以下不变量：
1. 两腿远端实仓的净裸露，绝不因为程序自己发出的减仓或补平单而增大。
2. 任何一个停开锁处于生效状态时，都不会发出开仓单。
3. 不会出现反向开仓，即平仓单让持仓穿过 0。
4. 每一笔开仓单都在硬上限之内：单腿 ≤150，总额 ≤600。
5. 影子模式下下单和撤单的调用次数为 0。
6. 存在非终态订单或裸露时，最多 N 步之内就会进入恢复路径（N 由你定义，并写进交接）。
7. HALTING 最终只会进入两种状态之一：实仓清零后转为 HALTED，或者持续重试。不会卡在一个无法再前进的状态。

不变量一旦失败，就输出种子和步骤序列，方便复现。
