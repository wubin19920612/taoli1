# M2 后端内存结构性瘦身：规划（Claude，2026-10-25，待用户确认）

## 1 截至目前的证据

| 时间 | 配置 | 1 小时 OOM | 结论 |
|---|---|---|---|
| 08:09–09:09 | 768m，S2 后基线 | 4 | 启动 254MB → 60 秒内约 580MB → +7MB/分钟 → 尖峰越过上限 |
| 09:12–10:12 | 768m + `MALLOC_ARENA_MAX=2` | 7 | 内存碎片不是主因，已回滚 |
| 11:34–12:34 | 768m + M1-C（去重复拷贝、目录刷新延后） | 5 | 启动跳涨少约 35MB，OOM 无改善 |
| 12:50–13:23 | **1024m** | **0**（33 分钟） | 后端涨到约 740MB 后增长放缓（1–2MB/分钟），整机可用最低 378MB |
| 13:25–13:38 | 1024m + tracemalloc | 5（13 分钟） | tracemalloc 开销约 +300MB，撑满 1024m；守护脚本在整机可用 148MB 时自动关闭 |

**tracemalloc 快照**（6 份，都是每次重启后约 1 分钟的常驻内容，Python 层统计）：

| 位置 | 大小 | 对象数 | 解读 |
|---|---|---|---|
| `json/decoder.py:354` | 74–76MB | 约 120 万 | **原始 JSON 解析结果被长期持有** |
| `copy.py:71` | 50MB | 约 8 万 | pydantic `model_copy`，市场快照及其副本 |
| `main.py:280` | 30MB | 约 8 万 | 只有文件名，多半是 pydantic 内部 `main.py`（模型构造） |
| `main.py:468` | 15MB | 约 7500 | 同上，待确认 |

**本机复现**（采集链 + 身份目录刷新，25 帧调用栈）：常驻的 JSON 只有 1.9MB（主要是 Lighter、Arcus 适配器）。所以线上那 74MB **不是采集链造成的**，而是本机没有运行的其他后台任务。

**已确认的一个具体问题**：`TradeAvailabilityService._cache`（`trade_availability.py:413-444`）把原始 JSON 整份缓存，只在读取时检查 20 秒 TTL，**过期条目永远不会删除**；没有指定 `cache_key` 时用完整 URL 作键，每查询一个新币种就多一个永久条目。本机实测单个大接口解析后约 1.5–4.6MB（Binance 合约 exchangeInfo 4.5MB、全币种充提网络 4.6MB、Bitget 现货 4.0MB 等）。它能解释一部分常驻 JSON 和持续增长，但大概解释不了全部 74MB。

## 2 判断

- 1024m 已经让 OOM 从每小时 4–5 次降到 33 分钟 0 次，后端在约 740MB 附近趋于平稳。**短期稳定已基本达到**，但余量只有约 280MB，整机可用 380–560MB，仍然偏紧。
- 能明显降低内存的方向有三个，按收益和风险排序：
  1. **原始 JSON 缓存治理**（预期 −30~70MB，风险低）：给 `TradeAvailabilityService._cache` 加过期清理和条目上限；把同类“缓存原始 payload”的写法全部找出来，改成只保留解析后需要的字段，或加 TTL/上限。
  2. **定位剩下的 JSON 持有者**（不改业务）：在 M1-A 探针里加一个默认关闭的“缓存规模普查”，按服务列出已知缓存的条目数，并用 `sys.getsizeof` 递归估算大小（每 5 分钟一次，有时间上限）。不用 tracemalloc，开销可控。
  3. **市场快照瘦身**（预期 −50~100MB，风险中高，工作量大）：`MarketSnapshot` 有约 60 个字段，每轮 1.05 万个对象，外加 `model_copy` 链。可选做法：(a) 只拷贝需要改的行（M1-C 已在身份校验里做了一部分）；(b) 发布前丢掉上一代快照的引用，避免新旧两代同时存活；(c) 长期把内部表示换成 `__slots__` dataclass，只在 API 边界转成 pydantic。(c) 牵涉面很大，要单独评估。

## 3 建议的实施顺序

| 阶段 | 内容 | 依赖 | 部署后验收 |
|---|---|---|---|
| **M2-1** | `TradeAvailabilityService._cache` 过期清理 + 条目上限（如 256），带测试；顺便查 `trade_availability.py` 里每分钟约 4 次的 `RuntimeError: 聚合行情中未找到指定原始市场`（只读，先报告原因） | 无 | 内存平台期下降；功能测试不变 |
| **M2-2** | 探针加“缓存规模普查”（默认关闭），上线后跑 1 小时，找出其余的原始 JSON 持有者 | M1-A | 得到按服务排序的缓存大小表 |
| **M2-3** | 按 M2-2 的结果逐个治理（同 M2-1 的模式） | M2-2 | 平台期再降 |
| **M2-4** | 评估“发布前释放上一代快照”和 `MarketSnapshot` 轻量化，先出设计和本机测量，不直接改 | M2-3 | 设计评审 |

目标：后端稳定在 **600MB 以下**，尖峰不超过 800MB。达到后再讨论限额能否回到 768m，或者维持 1024m 作为余量。

## 4 暂不建议

- 再开 tracemalloc：在当前内存规模下，开销约 +300MB，1024m 也撑不住。
- 加 swap 作为主要手段：只能缓解，不能解决问题，还会让 SQLite 和接口延迟变得不可预测。
